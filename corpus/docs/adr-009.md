# ADR-009: Back the feature store with Redis

- Status: Accepted
- Decided by: Jun
- Date: 2026-09-01
- Affected services: feature-store
- Related project: Project Vega, Project Zephyr

## Context

The fraud models now score every payment attempt inline, and the online lookup of merchant and card velocity features
has a budget of 15 ms at p99. Our current online store is a set of Postgres tables behind a small read API, and it
sits at 22-40 ms p99 under normal load and much worse during settlement windows, when it competes with batch reads.

We looked at three options: tuning the Postgres store (read replicas plus aggressive caching), a managed key-value
store, and a Redis cluster run by the platform team on our own Kubernetes nodes.

## Decision

The online layer of the feature store moves to Redis (cluster mode, three shards with one replica each). Features are
written as hashes keyed by entity id, with a TTL per feature group. The offline copy of every feature stays in the
analytics warehouse, which remains the source for training sets and backfills.

## Consequences

- Online reads should land well under the 15 ms budget; the load test on staging showed 3 ms p99.
- We lose ad-hoc SQL over online features. Debugging goes through the offline copy instead.
- Backfills now have to write to both the warehouse and Redis. The backfill job gets a dual-write mode and a
  verification step that samples 1% of keys.
- Memory sizing has to be revisited each quarter as new feature groups are added.

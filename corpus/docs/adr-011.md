# ADR-011: Reduce PCI scope by tokenizing card data at payments-api

- Status: Accepted
- Decided by: Uma
- Date: 2026-09-22
- Affected services: payments-api, checkout-web
- Related project: Project Nova, Project Atlas

## Context

Our last PCI DSS assessment put the checkout frontend, the payments API, the ledger service and two internal tools in
cardholder-data scope, mostly because raw card numbers pass through the browser bundle into our own API and then show
up in request logs. Every system in scope adds weeks of evidence collection to the annual audit, and the logging
incident from July (PAN fragments in debug logs) shows how easy it is to widen scope by accident.

## Decision

Card data is tokenized at the edge of payments-api. The checkout web client loads the card form from the
tokenization iframe, which posts the card number directly to the tokenization endpoint and hands back an opaque token.
From that point on, only the token travels through our systems. Payments API is the only service that can exchange a
token for a network charge, and it never logs the request body.

## Consequences

- Checkout web, the ledger service and the internal tools drop out of cardholder-data scope once the migration is
  complete. Payments API stays in scope and gets the stricter controls.
- The checkout form loses some styling freedom because the card fields live inside the iframe.
- Debug logging on payments-api is disabled for the tokenization and charge routes; tracing uses redacted spans.
- Security will re-run the scoping review after the Project Atlas checkout redesign ships.

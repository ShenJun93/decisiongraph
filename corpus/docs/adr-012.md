# ADR-012: Replace Kafka publishing for ledger events with a Postgres transactional outbox

- Status: Accepted
- Decided by: Omar
- Date: 2026-10-02
- Affected services: ledger-service
- Supersedes: ADR-007
- Related: ticket LED-41, #ledger thread of 2026-09-25

## Context

ADR-007 had the ledger service write each entry to Postgres and then publish it to Kafka as a second step. In
practice that gap has hurt us twice over:

1. Ticket LED-41: after consumer group rebalances, the reconciliation consumer replayed batches it had already
   applied, and we saw duplicate ledger events downstream. Finance caught a double-counted settlement on 2026-09-24.
2. The nightly gap check keeps finding entries that were committed with no event at all, because the process
   restarted between the database commit and the publish.

The #ledger discussion on 2026-09-25 concluded that tuning consumer offsets treats the symptom. The root problem is
that the database and the topic can disagree.

## Decision

The ledger service writes each ledger entry and its outgoing event row into an `outbox` table in the same Postgres
transaction. A relay process reads committed outbox rows in order, publishes them to the existing `ledger-events`
topic, and marks them sent. Every event carries the entry id as an idempotency key, so consumers can drop repeats.

The ledger service no longer writes to Kafka directly. The topic and its schema stay the same, so consumers do not
need to change.

## Consequences

- An event exists if and only if the entry committed. The nightly gap check can be retired after a month of clean
  runs.
- Delivery stays at-least-once; consumers still need the idempotency key, but duplicates no longer come from our side.
- The outbox table needs a retention job and a backlog alert (tracked in LED-44).
- Adds one small long-running relay to operate on the Kubernetes platform.
